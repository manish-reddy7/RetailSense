# RetailSense

**A disagreement-triggered multi-agent framework for daily demand forecasting and restocking.**
Research capstone: does disagreement between specialised forecasting agents predict forecast
error, and does deliberating only on high-disagreement cases beat always or never deliberating?

Four agents (Historical, Calendar, Weather, Trend) forecast daily demand 1-7 days ahead. The
orchestrator computes a normalised disagreement score D. Below a threshold tau it takes the
confidence-weighted consensus. At or above tau, an LLM critic explains the conflict and each agent
gets one bounded revision round. Code computes the final number, and the LLM never writes a
forecast or an order quantity. The forecast drives an (s, S) inventory policy, and every system
runs through the same simulator.

- **Data:** an India kirana (neighbourhood grocery) chain, store MUM_1 (Mumbai), 60 items,
  daily from 5 Jan 2019 to 28 Apr 2024. Sales, prices and the interest index are generated by
  `retailsense.data.india_generator` from `configs/india_generator.yaml` (fixed seed); weather
  (Open-Meteo) and the festival calendar are real. It is replayed data, not live POS data.
- **Spec:** `docs/RetailSense_Complete_Project_Blueprint.pdf`. Progress and every metric:
  `docs/PROGRESS.md`. Final results: `reports/RESULTS.md`.

## Setup

Python 3.11.

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
cp .env.example .env                 # then fill it in (never commit .env)
```

The LLM is configured in `configs/experiment.yaml` (`deliberation:`). The default is a local
Ollama model (`llama3.1:latest`): install Ollama, run `ollama pull llama3.1` and keep
`ollama serve` running (start it with `OLLAMA_NUM_PARALLEL=4` to match
`deliberation.workers: 4`). No API key is needed. `.env` holds a key only if you switch the provider:

| Key | Needed for |
|---|---|
| `OPENROUTER_API_KEY` | `provider: openrouter` |
| `GOOGLE_API_KEY` | `provider: google` |

## Data

```bash
python -m retailsense.data.india_generator   # writes data/raw/india/ (sales, calendar, prices, trends/)
```

Weather comes from the Open-Meteo historical archive for Mumbai and is fetched and cached in
`data/cache/openmeteo` automatically. Every API and LLM response is cached on disk under
`data/cache/`. Sharing that folder lets someone else rebuild the results without any API calls.

## One-command reproduction

```bash
bash reproduce.sh              # full pipeline; LLM answers come from the cache when present
bash reproduce.sh --offline    # rebuild from the cache only; an LLM cache miss is an error
```

The steps, which can also be run one by one:

| Step | Command | Output |
|---|---|---|
| Data | `python -m retailsense.data.india_generator` | `data/raw/india/` |
| Item subset | `python -m retailsense.data.load` | `configs/subset.yaml` |
| Signals | `python -m retailsense.data.weather` (and `.trends`) | `data/processed/india/*.parquet` |
| Features | `python -m retailsense.data.features` | `data/processed/india/features.parquet` |
| Agents + baselines (validation) | `python -m retailsense.eval.run_experiment --phase 2` | MLflow `india_phase2` |
| H1 on validation | `python -m retailsense.eval.h1_analysis` | `reports/india/h1_*` |
| Deliberation arms (validation) | `python -m retailsense.eval.deliberation_eval [--freeze]` | `reports/india/phase3b_*` |
| Inventory (validation) | `python -m retailsense.eval.inventory_eval` | `reports/india/phase4_*` |
| **Final test run** | `python -m retailsense.eval.run_experiment --final` | `reports/india/final/`, MLflow `india_phase5` |
| **Next-week forecast + orders** (after the experiment) | `python -m retailsense.forecast_future` | `reports/india/future_forecast.csv` |
| Pipeline dry run (validation, stub LLM) | `python -m retailsense.eval.run_experiment --dry-run` | `reports/india/dryrun/` |

**The test split is touched once.** `--final` refuses to run unless tau is frozen in the
config (`deliberation_eval --freeze` sets it from validation). It also writes
`reports/india/final/RUN_LOCK.json` and refuses to run again under a different config.

## Dashboard

```bash
streamlit run app/streamlit_app.py
```

It has four views: **Forecast** (agents with bands, D against tau, deliberation badge, action),
**Explain** (key factors, critic report, initial vs revised forecasts, why the action),
**Evaluate** (all tables and figures) and **Live**. Live is **demo mode**: it shows today's
Open-Meteo forecast for Mumbai next to a replayed item's stored forecasts, and falls back to
cached responses if the API fails. The dashboard reads SQLite and `reports/` and never re-runs
a model.

### Web app (Next.js)

A second front end in `web/` uses Next.js, TypeScript, Tailwind CSS, shadcn/ui, Apache
ECharts, TanStack Query, Lucide and Framer Motion. It is a static site that reads JSON exported
from the stored results:

```bash
python -m retailsense.web_export                   # exports SQLite + reports/ to web/public/data/
cd web && npm install && npm run dev               # http://localhost:3000
npm run build                                      # static site in web/out/
```

Its views are the same four (Forecast, Explain, Evaluate, Live demo), plus an Overview.

MLflow UI: `mlflow ui --backend-store-uri sqlite:///mlflow.db`.

## Honest scope

Sales are generated by a documented simulator with known drivers (`ground_truth.parquet` logs
every demand multiplier), so results show how the method behaves when the true drivers are
known, not how a real store performs. Weather is observed weather used as a perfect forecast; a
noise ablation tests that assumption. The interest index is a demand proxy. Inventory is
simulated. Results are reported whether RetailSense wins or not.
