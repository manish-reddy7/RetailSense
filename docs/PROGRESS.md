## Phase 1 — Historical + Calendar agents, baselines (2026-09-29)

### Built
- `data/features.py` → `data/processed/india/features.parquet`, with `available_at` per row.
- `eval/baselines.py`: seasonal naive (same weekday last week); ETS(A,N,A) with period 7 per item,
  refit weekly on a trailing 364-day window.
- `agents/historical.py`: LightGBM Tweedie + quantile (0.1, 0.9) models, early-stopped on the
  last 28 train days, then refit on the full train split. Also writes `oof_baseline.parquet`
  (5 expanding folds).
- `agents/residual.py` + `agents/calendar.py`: calendar residual adjuster fit on the OOF residuals.
- `agents/confidence.py`: trailing 28-day WAPE confidence with a department-level fallback when
  an item has fewer than 14 days.
- `eval/metrics.py`, `store/tracking.py` (MLflow), `eval/run_experiment.py --phase 1`.
- The leakage suite caught two leaks that were planted on purpose.

### Decision (2026-09-29): one model per horizon (approved)
A single direct model with every sales lag ≥ 7 ignores the last 6 days at h1. It is replaced by
one model per horizon h, whose features use data up to t − h: `lag_h`, `lag_7/14/28`, rolling
statistics on the lag-h series, and the price from the last closed week before t − h. The
Calendar residual agent is trained on OOF residuals pooled over all horizons. Confidence uses the
h=1 track record (the disagreement horizon).

## Phase 2 — External context: Weather and Trend, control model (2026-09-29)

### Built
- `data/weather.py`: Open-Meteo archive for Mumbai (cached in `data/cache/openmeteo`); ten earlier
  years feed only the climatology. Features: tmax/tmin/precip, anomalies vs a ±15-day same-season
  climatology from the previous 10 years only, hot-day and rainy-day flags, 3-day changes.
  **Observed weather is used as a perfect forecast for the target day** (blueprint §4.2
  limitation). A noise ablation tests it.
- `data/trends.py`: parses Trends-format CSVs, stitches overlapping windows by the overlap ratio,
  and builds only **scale-invariant** features (ratio to trailing 52-week mean, 4-week change,
  52-week z-score). A week becomes available on the day after it ends.
- `features.join_context`: weather joins on the target date; interest joins as-of t − h.
- `agents/weather.py`, `agents/trend.py`: residual adjusters using only their own features.
- Control model: the per-horizon LightGBM trained on every feature.

### Validation metrics (MUM_1, 60 items)
| System | h1 WAPE | h1-7 WAPE | h1 coverage |
|---|---|---|---|
| Seasonal naive | 0.510 | 0.510 | – |
| ETS | 0.373 | 0.382 | 0.811 |
| Historical | 0.379 | 0.387 | 0.786 |
| Historical + Calendar | 0.373 | 0.383 | 0.785 |
| Historical + Weather | 0.383 (**worse**) | 0.392 | 0.766 |
| Historical + Trend | 0.383 (**worse**) | 0.391 | 0.754 |
| LightGBM, all features (control) | **0.367** | **0.376** | 0.781 |

### Key finding: the context agents cannot target the evidence to the right items
Checked against the ground truth: the Weather and Trend agents apply about the same adjustment to
every item. Weather adds about +2 units to soap and atta (true weather effect 0) and +2.3 to tea
(true −1.4). Trend adds a flat +1.3 to every item, while the true ice-cream shock effect is +11.7.
Their correlation with the planted effects is 0.5–0.65 *within* sensitive items but 0.02 overall
for Trend. Cause: the blueprint gives a residual agent only "baseline + its own features", with
no item identity, so department-level signals cannot be routed to the items they affect.

### Other notes
- The validation window (Dec–Mar) is a poor test of weather and festival evidence for Mumbai: 60
  hot-day points, 0 rainy days, no major festival. The test window has Holi and Eid.
- Confidence is weak: Spearman −0.09 to −0.12, and the most confident agent is the most accurate
  on only 33 % of points, which is chance with 4 agents.

### Open decision
Should the context agents receive item identity (category or item_id) alongside their own
evidence? This changes the blueprint's "own features only" rule, so it needs approval.

## Phase 3a — Disagreement score and H1 on validation (2026-09-29)

### Built
- `orchestrator/disagreement.py`: consensus weights, D (confidence-weighted CV, floor 1),
  D_range, D_std, route, and a vectorised `score_table` that refuses missing agents instead of
  silently dropping them. Tests include scale invariance and identical forecasts giving D = 0.
- `eval/h1_analysis.py` (a script, not a notebook): Spearman ρ(D, relative error), AUROC for the
  worst 20 %, 1,000-sample bootstrap CIs over items, D deciles, drop-one-agent, per-volume-tertile
  results, reference signals, the added value of D, and the trigger sweep. Writes
  `reports/india/*.csv` and `reports/figures/india/`, logs to MLflow `india_phase3a`.

### H1 results (validation, h=1, 4 agents)
- D: ρ = 0.064 [0.026, 0.102], AUROC worst-20 % = 0.535. Within volume tertiles about 0.
- D adds nothing beyond the Historical band width and item volume.
- Provisional τ = 0.0769 (80th percentile of validation D). **Not frozen.**

### Verdict
H1 holds only in the weakest sense (ρ > 0 with a CI excluding 0). As implemented, D is a weak
trigger. Likely cause: every context agent is the shared baseline plus a small adjustment, so D
measures the size of the adjustments, not real uncertainty. The test split was not used.

## Phase 3b — Critic and bounded revision (2026-09-29 – 2026-09-30)

### Built
- LLM client with providers `ollama` (local), `openrouter` and `google`: disk cache keyed by
  model, prompt version, prompt text and input; JSON-schema output; one retry, then fallback to
  the fast path; one lock per cache key (thread-safe).
- Critic and revise prompts v1, `apply_revision` (code clips m and y and computes the number),
  LangGraph, SQLite logging, mocked tests.
- LLM: local Ollama `llama3.1:latest` (8B) on an RTX 4050, temperature 0, fixed seed, 1 worker.
  `context_tokens` 3072 (largest prompt 898 tokens) so 26 of 33 layers fit in the 6 GB GPU.
- Earlier pilot on OpenRouter `google/gemini-2.5-flash-lite`: 100 % hold rate, so deliberation
  changed no forecast with that model. It was replaced by llama3.1.

### Full validation run, prompt v1 (2026-09-30) — superseded, see below
1,500 stratified validation cases, τ = 0.0769, 5,094 LLM calls.

| arm | WAPE | trigger rate | LLM calls / 1000 forecasts |
|---|---|---|---|
| no_deliberation | 0.3771 | 0 | 0 |
| always_on | 0.3779 | 1.0 | 5,017 |
| selective (D ≥ τ) | 0.3773 | 0.20 | 1,001 |
| random, same rate (mean of draws) | 0.3773 (sd 0.0002) | 0.20 | 1,003 |

- H2 on the 300 triggered cases: 28.7 % improved, 31.3 % worsened; mean |err| 9.86 → 9.89;
  Wilcoxon p = 0.75.
- Gates: trigger rate 20 % (inside 10–30 %); hold rate 49.6 % (historical 35 %, calendar 51 %,
  trend 53 %, weather 60 %), so the prompt is not coercive; fallback 0 %; clip rate 0 %.
- The cost–accuracy curve is flat (0.3771–0.3779 WAPE at every trigger rate).
- Reading: deliberation did not improve accuracy and selective was no better than random.

### Prompt fix (2026-09-30) — the run above must be repeated
The critic described the Calendar agent's evidence as including "SNAP days", a U.S. programme;
the India calendar has no SNAP (the columns exist only for the shared file layout and are always
0). `EVIDENCE["calendar"]` in `orchestrator/critic.py` now reads "weekday, month, holidays and
festivals". Because the prompt changed, every critic and revision answer is new, so the full
validation run is repeated before τ and the prompt are frozen.
