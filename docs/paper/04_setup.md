# 4 Experimental setup

## 4.1 Data

The data describe a kirana (neighbourhood grocery) chain in India. We use store MUM_1 (Mumbai)
and all 60 of its items, ranked by total sales over the training days only, so test sales cannot
influence which items are chosen. Daily sales, prices, promotions and a weekly search-interest
index are generated by a documented simulator with a fixed seed; weather (Open-Meteo) and the
festival calendar (Diwali, Holi, Eid, Dussehra and national holidays) are real. Demand is the
product of a base level, weekday, growth, weather, festival, payday, promotion and interest-shock
multipliers, with gamma-Poisson noise and occasional stock-outs. Every multiplier is logged per
row, so we know which evidence source actually drove demand on each day. The data are replayed;
there is no live point-of-sale feed.

| Split | Days | Dates | Use |
|---|---|---|---|
| Train | d_1-d_1799 | 5 Jan 2019 - 8 Dec 2023 | fit every model (with internal expanding folds) |
| Validation | d_1800-d_1885 | 9 Dec 2023 - 3 Mar 2024 | early-stopping choice, confidence, calibration of tau, all design decisions |
| Test | d_1886-d_1941 | 4 Mar - 28 Apr 2024 | final numbers, one run |

The split is chronological. Every model is fitted on train. Validation and test forecasts are
made from rolling daily origins with the same models, and each origin uses only data revealed up
to that origin. The rolling-origin backtest (Section 5) repeats the evaluation on three 56-day
windows before validation (d_1632-d_1687, d_1688-d_1743, d_1744-d_1799). For each window, every
model is refitted on the days before it.

## 4.2 Signals and assumptions

- **Leakage control.** Every feature row carries an `available_at` date, and tests assert that
  no feature is available after the prediction time. Actual demand is reachable only from
  evaluation code.
- **Weather.** Daily weather comes from the Open-Meteo historical archive for Mumbai. It is
  *observed* weather used as a perfect forecast. This is a stated limitation. An ablation adds
  forecast-like noise (Section 5).
- **Interest signals.** The weekly interest index comes in Google Trends format, in two
  overlapping windows each scaled to its own maximum. A week counts as available only after it
  closes, and only scale-invariant features are used. It is a demand *proxy*.
- **Missing signals.** A missing signal is left missing, never zero-filled or forward-filled.

## 4.3 Systems compared

| # | System | Isolates |
|---|---|---|
| 1 | Seasonal naive (same weekday last week) | floor |
| 2 | ETS(A,N,A) per item, weekly season | classical baseline |
| 3 | One LightGBM with all features | does splitting evidence into agents beat one model? |
| 4 | Historical agent only | value of context |
| 5 | Multi-agent simple average | value of combining |
| 6 | Multi-agent confidence-weighted, no deliberation | value of confidence weighting |
| 7 | Random-trigger deliberation at RetailSense's rate | value of D as the trigger |
| 8 | Always-on deliberation | upper bound; cost reference |
| 9 | RetailSense (D >= tau triggers deliberation) | proposed method |

Systems 7-9 share one set of deliberation outputs per forecast point. tau is not in any prompt,
so the arms are paired subsets of the same LLM answers.

## 4.4 Metrics and tests

- **Forecast metrics.** MAE, RMSE, WAPE (primary) and sMAPE at h = 1 and pooled over h = 1-7,
  plus 10-90% band coverage. Each comes with 95% confidence intervals from a bootstrap over
  items.
- **Mechanism metrics.**
  - H1: Spearman correlation between D and relative absolute error, AUROC of D for the worst 20%
    of errors, and a decile plot.
  - H2: the share of triggered cases improved or worsened by deliberation, and a Wilcoxon test.
  - Cost: LLM calls, tokens and latency per 1,000 forecasts.
  - The cost-accuracy curve over trigger rates from 0% to 100%.
- **Inventory.** Every system runs through the same daily simulator (Section 3.5) with holding
  cost 25% of price per year, order cost $5 and lost-sales cost equal to 1x price. Reported:
  stockout rate, fill rate, overstock and total cost.
- **Statistics.** RetailSense is compared with each other system using:
  - a Diebold-Mariano test on daily mean absolute error (plus per-item tests);
  - a paired bootstrap over items (1,000 resamples) for WAPE and cost differences;
  - a Wilcoxon signed-rank test on per-item WAPE.
- **Ablations.**
  - Calibrated vs fixed tau.
  - D vs D_range vs unnormalised D.
  - Weights-only vs weights-and-values revision.
  - Dropping each context agent.
  - Noisy weather forecasts.
  - Lead time 1, 3 and 7 days.
- **Software and tracking.** All runs are logged to MLflow with the config hash and git commit.
  Per-case outputs go to SQLite. The unit and leakage tests run on every change.
